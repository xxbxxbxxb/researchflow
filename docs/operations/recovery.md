# 恢复和故障边界

一个任务可以有多次研究运行，每次运行有固定输入清单。崩溃恢复沿用原 run_id，主动重新研究建立新 run_id。队列认领与租约更新使用数据库时钟；当前 Worker 的 owner/epoch/lease/cancel 标志必须在每个提交事务内检查。

业务阶段先查 StepReceipt。业务输出和凭据在同一事务中提交，因此“报告已提交，但 checkpoint 尚未保存时崩溃”不会在恢复后生成第二份报告。LangGraph checkpoint、pending writes 和工具提交也使用同一 fence；在内存里先检查 ownership，再另开事务保存，不构成保护。

租约五秒，heartbeat 默认每秒。接管增加 epoch，旧 Worker 的迟到输出、原文登记和 checkpoint 都被拒绝。取消会传播到当前协程与 HTTP/PDF解析子进程；就算远端继续计算，迟到结果也不能写回。真实进程故障测试分别在 evidence/report 提交后杀死子进程，再由新 Worker 恢复。

活跃预算由锁定的数据库时钟累计，Worker 与可选预览不会重复计同一段时间。单次操作的超时仍使用当前进程的 monotonic clock。崩溃的不确定片段保守计至旧租约结束；人工审阅等待不计活跃时间。已预留模型调用不因为未知结果而退款。

代码、关键依赖、模型和策略版本改变时，应创建新运行。保守的源码指纹可能连兼容的小修也拒绝恢复，这是保持输入/实现可追踪的取舍；旧报告、知识和原文仍可查看。界面允许从 interrupted 任务建立新运行。

外部模型调用不是 exactly-once。提供商返回成功与本地提交之间发生故障时，下一次可能再次收费。StepReceipt 保证本地业务提交不重复，不能把这一保证扩展为远端服务只执行一次。
